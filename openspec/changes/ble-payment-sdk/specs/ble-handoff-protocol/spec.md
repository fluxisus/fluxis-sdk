## ADDED Requirements

### Requirement: Single normative protocol document
The Fluxis BLE Protocol SHALL be specified in `docs/ble-protocol.md`, version 3 (preview only), and every BLE SDK SHALL implement that document. Version bytes `0x01` and `0x02` are reserved and SHALL be rejected.

#### Scenario: Prototype record is rejected
- **WHEN** a payer reads a RECORD whose first byte is `0x02`
- **THEN** decoding fails with `unsupported_version` and the collector is not offered as a candidate

### Requirement: Read-only preview, no claim
The collector SHALL expose only readable, unencrypted attributes (RECORD and PREVIEW) and SHALL NOT offer any claim, lock or writable attribute. Every payer in range MAY read the active sale; the payer is whoever pays through the Fluxis API.

#### Scenario: Two wallets at once
- **WHEN** two wallets read the PREVIEW of the same collector
- **THEN** both receive the same session id and content, and the collector keeps advertising

### Requirement: PREVIEW value
PREVIEW SHALL be `version u8 (0x03) | sessionId (16) | kind u8 | content`, at most 512 bytes. Kind `0x01` carries the NASPIP token as UTF-8 (1–494 bytes); kind `0x02` carries the 16-byte POS id and is used only when the token doesn't fit. Decoding SHALL be strict (exact lengths, no trailing bytes, known kinds only).

#### Scenario: Staging POS token
- **WHEN** the collector publishes a 431-byte NASPIP token
- **THEN** PREVIEW is 449 bytes with kind `0x01`, read by the payer with a long read

#### Scenario: Oversized token
- **WHEN** the token is 495 bytes or longer and a POS id was given
- **THEN** PREVIEW is 34 bytes with kind `0x02`; without a POS id, `start` fails with `preview_too_large`

### Requirement: Amounts in minor units with explicit scale and currency
The discovery record SHALL encode an optional amount as an unsigned 64-bit count of minor units (at most 2^63−1), a scale from 0 to 18, and a currency code of 0–12 characters from `[A-Z0-9]`. The record is an unauthenticated hint.

#### Scenario: Two-decimal fiat amount
- **WHEN** a collector starts with amount `12.50` and currency `ARS`
- **THEN** the record carries `minorUnits = 1250`, `scale = 2`, `currency = "ARS"`, and payers format it as `ARS 12.50`

#### Scenario: Open-amount session
- **WHEN** a collector starts without an amount
- **THEN** the record's `AMOUNT_PRESENT` flag is clear and no amount fields are encoded

### Requirement: Wallets verify through the API
Wallets SHALL show the merchant returned by `POST /public/qr/read` and the amount returned by `GET /public/checkout/pos/{posId}`, never the record hints, and SHALL re-check that the payment request is still pending right before signing.

#### Scenario: Another wallet paid first
- **WHEN** a wallet's user taps *Pay* after another wallet already paid the same request
- **THEN** the re-check shows the request is no longer pending and the wallet doesn't sign

### Requirement: Shared conformance vectors
`packages/ble/test-vectors/vectors.json` SHALL be generated by the reference implementation, and every SDK SHALL run all of it in CI, including exact error strings.

#### Scenario: Stale vectors
- **WHEN** the reference implementation changes without regenerating `vectors.json`
- **THEN** `generate_vectors.py --check` fails in CI
